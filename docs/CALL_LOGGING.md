# 通话日志与真实验收

全双工 `/api/voice/realtime` 每次连接独立生成通话 ID，默认保存到 `logs/calls/<UTC日期>/<通话ID>/`。接通时页面显示“日志记录中”和 ID 后八位。`CALL_LOG_DIR` 可指定其他目录；目录和录音不通过网页/API公开，已排除 Git，文件权限为 0600。密钥与 Authorization 会脱敏，连接头不写入日志。

## 文件

- `events.jsonl`：按序号追加事件，含服务器 UTC 时间、服务器单调时钟、通话 ID、话轮与响应/item ID。包含上下文和生效提示词、双方转写、供应商原始协议事件、工具参数和结果、取消与截断、丢弃旧音频的原因、静音、错误及浏览器播放回执。
- `input.wav`：实际收到并发送模型的连续 16 kHz、16-bit、单声道麦克风 PCM；静音期间为零帧。
- `model-output.wav`：供应商生成的所有 24 kHz PCM 顺序拼接，包含未播放、被打断和被屏蔽的内部响应。**不能把它直接当作用户听到的完整录音。**每段 PCM 在 `provider.in` 音频事件中有文件偏移、长度和 response/item ID；偏移从 WAV 的 44 字节头之后计。
- `summary.json`：挂断/断线后关闭事件和音频流，修正 WAV 头，最后原子落盘的汇总；记录结束原因、字节数、事件数和完整性。该文件出现表示此次收尾完成。进程强制崩溃时可能没有汇总，此时按未完整收尾处理，可从事件和原始 PCM 排查。

收尾后在日志根目录原子发布 `<通话ID>.complete.json` 小索引，供监听器可靠唤醒；避免操作系统来不及监听新建子目录而漏掉极速结束的通话。

日志不在音频回调中等待磁盘。写入报错或积压超过 8 MiB 时明确报告日志错误并结束通话，不静默丢日志后继续宣称完整。正常服务关闭会等待各通话日志收尾。当前覆盖 WebSocket 接受之后的整段通话；浏览器授权或建立连接之前的失败尚无服务器会话日志。

## 时间线

浏览器 `diagnostic` 记录本地 VAD、实际调用停播、播放开始/结束、逐段 AudioContext 排程、播放游标、设备输出延迟、持续采集计数/间隙及标签页状态。时间均以该次浏览器拨号的单调时钟为基准；服务器接收时刻另存，不能把两个时钟直接相减。

`vad_started/stopped` 附带输入 PCM 的帧边界和估算首尾样本位置。`vadEstimatedOnsetToStopMs` 是 VAD 估算开口到软件停播；`detectionToStopMs` 是本地确认到调用 stop；`estimatedSpeechEndToScheduledPlaybackMs` 是估算话尾到音频时钟排定播放时间。另列 `observedSpeechEndToPlaybackCallbackMs` 和 `playbackCallbackLagMs`，因为主线程拥塞会延迟“已播放”回调，不能把晚到的回调当作实际扬声器起音时间。它们不等于实测扬声器或蓝牙的物理声学延迟。需要结合 `input.wav` 的波形/录音、设备输出延迟和用户现场体验验收。

`playback_chunk` 给出 response/item、item 内偏移和 AudioContext 排定起止；`playback_stopped` 给出停止原因及已听游标。由这些事件区分生成、发给浏览器、排入播放、被打断四个阶段。工具原始字幕即便被屏蔽也保存在 provider.in，实际下发的字幕在 browser.out；不会因为屏蔽而丢失诊断证据。

接答指标按响应所属话轮及输入 PCM 范围关联本地语音首尾，不能取任意上一条 `vad_stopped`。某轮本地 VAD 漏检时，`speechBoundarySource` 为 `unavailable`，话尾指标留空，只保留云端结束事件到播放的时间；它不包含完整的断句等待。云端先停播、本地后检测的情况也不计算负数“本地检测到停播”。

## 查看

```bash
npm run calls:inspect
```

读取最新一通（未结束时也可查看现有事件）。指定某一通目录：

```bash
npm run calls:inspect -- logs/calls/日期/通话ID
```

```bash
npm run calls:inspect -- --wait
```

通过文件系统事件等待启动后新建的一通结束，然后打印报告并退出；没有轮询。报告包括双方转写、工具列表、打断、接话、播放中收音、取消后的播放、错误及疑似工具播报。它只提供证据，不自动给出“全双工验收通过”。测试用目录在 `agent-tmp/calls/journal-*`，用户通话在默认 `logs/calls`，查看时确认通话 ID。

## 本次用户实测验收

用户实际通话后，再依据该通日志判断：

1. 多轮对话共用同一连接，导游讲话和工具执行期间仍持续收到麦克风音频。
2. 在导游讲话期间至少两次插话，旧播放及时停止，停止后不恢复旧音频；参考本地估算停播目标 300 ms 内，同时确认现场听感。
3. 插话的新问题有正确转写与对应新回答，分别报告开口停播、话尾接答延迟；工具等待另列。
4. 至少一次景点查询或路线规划正常执行；最终播报没有函数名、参数、JSON 或调用旁白，实际答案和工具事实一致。
5. 静音、恢复、短暂停顿和挂断正常；观察只听导游/提示音时有没有误触发。
6. 根据失败事件、双方音频和用户反馈列出通过项、失败项、未覆盖项，再判断是否完成。

增加日志时的夹具曾出现一次“把原始音量钢琴采样直接注入麦克风”触发 VAD，下一次运行通过；失败记录保留在 `agent-tmp/calls/journal-latency-fixture/2026-11-13/2026-11-13T16-10-30-658Z-72f7f0b0/`。这是待核验的检测边界，不能用一次复测通过替代实际回声与误打断验收。
